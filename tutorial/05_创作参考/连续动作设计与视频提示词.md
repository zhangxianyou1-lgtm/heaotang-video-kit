# 连续动作设计与视频提示词

2026-11-13 R5.2修订。先结合[动作提示词工程研究综述](动作提示词工程_研究综述.md)与[视觉隐喻及代码桥案例](视觉隐喻与口播适配_代码之桥案例.md)阅读。本文负责动作执行，不单独决定创意质量；不改变Claude自主设计动画的分工。具体物件与秒数不是全系列固定模板。

## 先写发生了什么，再写怎样拍

原 R5 已要求起止状态、动作过程和结果停留。本次补充把这些原则变成可执行检查，避免把“首尾图好看＋轻微推镜”当成动作完成。

先用一句话写明：**谁受什么驱动，从哪种状态，经由什么可见过程，变成什么状态。**

R5.1的“手推动工单夹、碰到键盘后停下”虽有因果，却仍过于保守，不能作为以后默认推荐。更有发展空间的例子是用户提出的代码之桥：代码状态决定桥的连接和承重，变化影响人物能否前行。先验证这种规则是否符合口播立场，再设计它如何被看见。

运动可以来自主体、相机、焦点或光线。相机运动若确实揭露之前看不见的关系，也有叙事价值。静场可以表现余味；应说明观众在看什么。问题在于需要发生变化的段落，被无目的的推拉摇移代替。

## 每段填写一张动作表

| 字段 | 要写到可以据此拍摄 |
|---|---|
| 视觉命题 | 画面增加的关系、矛盾或后果 |
| 主体与初态 | 谁在哪儿；手是否已接触；物体是否已运动 |
| 触发与接触 | 手推、脚蹬、重力、铰链、按钮等；谁作用于谁 |
| 连续过程 | 依次可见的2–4个动作阶段，属于同一事件，不是多件无关事 |
| 路径与幅度 | 朝哪边、移动到哪件物体附近；路径有没有障碍，手机观看能否辨认 |
| 速度与节奏 | 起动、推进、减速/受阻、收束；避免全段匀速小幅漂动 |
| 结果与停留 | 最后具体可见的状态，留多少时间辨认 |
| 相机与焦点 | 固定或一种主要运动；移动要服务观看，不抢主体动作 |
| 不变量 | 身份、左右关系、形状、数量、支撑、背景等最关键的连续性 |
| 口播与剪点 | 源时间、成片帧槽、关键词对应动作、接入和接出状态 |

一段先安排一个核心事件。复杂事件装不下，就减少步骤或使用有理由的剪辑省略，不靠加“丝滑、电影感、自然流畅”解决，也不让口播迁就画面变速。

## 写成给模型的提示词

先形成详细导演表，再压缩为一段明确的执行文本。参考图已经提供的美术不必反复堆写；简要锁定关键身份与空间，把篇幅留给动作。

> 以【具体首帧文件】为起点。【主体】已经处于【初态】。先【触发与接触】，接着沿【路径】完成【主要动作】，因此【另一物体/主体的可见反应】；最后【终态及结果保持】。相机【固定或一种运动】，焦点覆盖【关键接触处】。全程保留【必要不变量】。单个连续镜头／明确指定的剪切。

优先写正向过程：“脚掌踩稳一级，再将重心移上去”；仅在确有风险处补限制。不要同时写“所有物体固定”又要求道具移动。避免把终态写在开头，让模型从动作已完成的位置开始。

### 时间写法

导演表以实际成片槽精确分帧。模型提示词可用“先、随后、最后”及少量近似秒点帮助表达先后。秒点是意图，不是模型逐帧执行的保证。

平台生成长度与实际槽分开写。例如成片127帧/30fps=4.233秒，生成5秒时，核心动作应在约3.5秒前完成，余下为自然终态。下载后找到真正完成的可用区间再剪；不能固定取前127帧却把结果切掉。若动作装不下，重设计或重做受影响段，不拉伸口播。

### 参考帧要为动作准备

先设计连续路径，再制作首尾图。写实事件的首帧留出手脚、移动通道与支撑，尾帧延续需要保留的场景和结构。隐喻变形允许结构、材质或空间发生设计内的变化，要写清元素如何映射、转换沿哪里传播及什么保持不变。两张漂亮但缺少连接规则的图，不自动构成连续镜头。

发现首尾图不相容时，应修图或重建其中一张。不能为了保住已生成的图片，未经说明把连续动作降成两个静态推镜。明确设计的硬切可以保留：要说明省略了什么、视线和方向如何衔接，不能用硬切掩盖本应看到的关键过程。

需要跨片连续时，可用前一段实际尾帧作为后一段起点；还要核对姿态、速度、移动方向与道具位置，沿用图片本身并不保证运动无缝。

## 动态验收：技术成功之后还要看事件

1. 正常速度连续观看拟用区间，并结合前后口播检查动作落点。记录实际看过的文件与区间。
2. 对接触、受力、交接和停止位置慢放/逐帧检查；检查手指、脚掌、物体边界、轨迹和数量。超现实变化检查的是既定规则、变化前沿和因果，不强制真实材料物理。静态抽帧仅能辅助定位，不能单独证明动作流畅。
3. 将“动作是否发生”“物理连续是否成立”“叙事能否读懂”“技术参数是否合格”分别记录。不能用帧数、哈希、无黑屏或模型成功回执替代前面三项。
4. 假设相机固定，检查核心事件是否仍可辨认。若本来就是视角揭露，则检查相机移动究竟增加了哪条可见信息。
5. 在手机观看尺寸检查：关键动作是否太小；字幕是否遮住接触点；动作结果是否留有观看时间。
6. 给出实际源入点/出点、动作完成点、终态停留和需修复项。不具备动态观看条件时，动作连续性标“未验证”，不要用“抽帧通过”顶替。

## 检索依据及适用边界

检索日期：2026-11-13。以下是对官方方法的简要归纳；上面的动作表、质量门槛和项目实例是本项目新增执行约定，并非官方逐字规范。

- [MiniMax H3 官方基础提示词指南](https://huggingface.co/MiniMaxAI/MiniMax-H3/blob/main/docs/VIDEO_PROMPT_WRITING_GUIDE_base_en.md)：图生视频应从初态向前发展；首尾帧任务要写可观察的中间变化和连续路径。这里采用其动作组织思路，不将其完整重写格式当成 LibTV 的必填 API 字段。
- [Runway 官方图生视频指南](https://help.runwayml.com/hc/en-us/articles/48324313115155-Image-to-Video-Prompting-Guide)：提示词重点写运动与时间推进，可用自然顺序或近似时间点；参考图的运动暗示应与动作一致。该指南面向 Runway，借用方法不代表 H3 参数或成功率相同。
- [MiniMax 官方视频 API 说明](https://platform.minimax.io/docs/guides/video-generation)：模型服务具备首尾帧与参考生成入口。LibTV 是另一接入层，实际模式、时长、字数限制与可用参考类型仍以当次 CLI 查询为准，不能照搬 API 能力作为平台已支持的证明。

增加动作描述能让任务更明确，不保证一次生成就得到正确物理运动；提交后的真实结果决定是否通过。
