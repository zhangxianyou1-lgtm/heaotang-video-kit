# 微信支付与小程序：先认流程，再对版式

## 参考判定

| 画面类型 | 必须核对 |
| --- | --- |
| 个人转账 | 对方名字、是否仍待确认收款、按钮文字；支付成功不必然等于对方已收款 |
| 小程序商户支付 | 调起支付、支付结果、返回商户小程序分别是什么页面；实际参考里的返回按钮 |
| 物业自身回执 | 房屋、账期、缴费项目、支付方式及单号；它不是微信原生成功页 |

本次用户的小程序视频末帧是“返回商家”；此前个人转账截图是“完成”，还有“待…确认收款”。本次不能混用。微信历史官方资料也有“完成”版本，因此不能把“所有小程序永久使用返回商家”写成通则。后续逐次核对用户参考中的平台、版本、支付类型和文案。

## 这套已修正的视觉样本

参考画幅588×1280。比例仅用于本案例，不能当所有手机的固定尺寸：

- 白色页面；绿色支付气泡勾与“支付成功”横排，组中心约在屏高8.3%。不把圆勾放在文字上方。
- 商户名约在屏高19%，金额约在25%；本案例只遮商户名，金额317.60保留。
- 底部约86%处，宽约内容区46%、高约屏高5.5%的浅灰底黑字“返回商家”，没有绿色描边。
- 成功页无模拟手机边框、无小程序胶囊、无底部iOS横条。横版等比居中，不把手机内容横向拉伸；外围同白色。
- 安卓状态栏核对字重、间距、比例：模糊通知头像、时间、Wi-Fi及上下行、双卡4G、参考确有的漫游R、电量数字及边框。不要用一个灰圆点代替明显的通知头像，不凭记忆随意拼图标。
- 状态栏时间、电量、通知图案是创作设定，不读取或复制别人的身份。参考为iOS时重新按iOS处理。

## 可复用页面

`assets/wechat/mobile.html`及同目录JS/CSS是本地交互道具，无真实支付连接。默认隐藏外围导航；保留本案例的账单、付款层、成功页和回执；跨页流程须按本次参考重新验证。

- `mobile.html?capture=1#home`：账单入口。
- `mobile.html?capture=1#bill`：账单。
- `mobile.html?capture=1#wechat-paid`：独立支付成功；进入后页面为已缴状态，点击“返回商家”回账单。
- `mobile.html?capture=1&portrait=1#wechat-paid`：竖版录制入口。
- `mobile.html?capture=1#paid`：物业回执。

新项目先替换业务数据、商户匹配词、日期、编号和金额总计，再检查截图。有费用明细时，金额以账单计算结果为准，不能只改单张成功图。只有用户明确给定总额、且只需要独立成功页时，直接使用该总额，不为凑数据虚构物业账单或额外制作付款过程。重新录未缴账单前完整刷新页面，避免已缴状态残留。

## 录制与剪切

用户不想展示支付中间过程时，可保留账单镜头，硬切到成功页。不要以一段黑屏冒充密码验证，也不要虚构已经调起真实微信。当前案例05/05p是6秒账单＋12秒成功；09/09p另给12秒纯成功页。时长是本次选择，后续按口播决定。

要展示连续付款操作时，先核对完整参考中的弹出位置、背景遮罩、确认和返回关系，再录页面实际动作。不要“点微信支付立刻跳物业长回执”来替代缺失的一整段。若参考只有最终结果，不凭空声称看过中间流程。

单独成功页保持稳定，鼠标移开，不让hover、焦点框、浏览器边框或录制光标进入手机画面。检查点击返回后的实际已缴状态；不能只看到按钮文字就认为流程已完成。
